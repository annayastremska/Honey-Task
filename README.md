## Завдання 1. Атрибуція реєстрацій

**Відповідь:** частка неатрибутованих реєстрацій по джерелах.

| Джерело | Частка неатрибутованих | Можливий діапазон |
|---|---|---|
| google | 12,7% | 12,5–13,0% |
| facebook | 6,1% | 4,6–7,5% |
| tiktok | 21,7% | 18,7–25,3% |
| snapchat | ≈ 0% | 0–12% |

*⚠ Snapchat працював лише 14 днів — замало, щоб відрізнити його частку від нуля.*

### Дані
- `task1(attribution).csv`, 153 дні.
- `google`, `facebook`, `tiktok`, `snapchat` — атрибутовані реєстрації з джерела за день; `unattributed` — неатрибутовані за день, без джерела.
- День 12 виключено: усі колонки = 0, тобто даних нема, а не нуль реєстрацій.

### Метод
Джерела запускались по черзі: google з дня 1, facebook — 107, tiktok — 126, snapchat — 140. Тому частку кожного джерела видно в період після його запуску.

**Ланцюжок по періодах:**
1. Дні 1–106 працює лише google: частка google = неатрибутовані / (реєстрації google + неатрибутовані) = 3 340 / (22 882 + 3 340) = 12,7%.
2. Дні 107–125 додається facebook: з 545 неатрибутованих google за своєю часткою дає 447; решта 98 — від facebook; частка facebook = 98 / (1 526 + 98) = 6,1%.
3. Дні 126–139 — так само для tiktok, віднімаючи google і facebook.
4. Дні 140–153 — так само для snapchat.

**Діапазон:** 2 000 разів перебираємо дні всередині кожного періоду і перераховуємо ланцюжок; середні 95% результатів — діапазон.

**Перевірка:** частки всіх джерел одночасно підбираються однією регресією по всіх днях (неатрибутовані за день = Σ реєстрації джерела × його коефіцієнт). Якщо частки ланцюжка й регресії розходяться більш ніж на 1 в.п., частка джерела нестала в часі.

| Джерело | Ланцюжок | Регресія | Різниця, в.п. |
|---|---|---|---|
| google | 12,74% | 12,74% | 0,00 |
| facebook | 6,06% | 6,42% | −0,36 |
| tiktok | 21,72% | 20,77% | 0,95 |
| snapchat | −6,95% | −0,44% | −6,50 |

- Google, facebook і tiktok — розбіжність у межах 1 в.п.
- Snapchat — обидва способи дають від'ємну частку, тобто частку на 14 днях не відрізнити від нуля; верхня межа — 12%.

*⚠ З 107-го по 147-й день `facebook` рівно дорівнює `google / 2`. Тому частки google і facebook у ці дні не розділяються самі по собі, і частка facebook спирається на частку google з днів 1–106.*

*⚠ Метод припускає, що всі неатрибутовані приходять з реклами. Частку «органіки» (неатрибутованих без джерела) на цих даних надійно відділити від google не вдалося.*

### Код
Ланцюжок (`task1/attribution.R`):

```r
# У періоді нового джерела віднімаємо очікуване від старих; решта — від нового
chain_shares <- function(d) {
  totals <- period_totals(d)
  shares <- c()
  for (i in seq_along(sources)) {
    new_source <- sources[i]
    p <- totals[totals$period == i, ]

    expected <- 0
    for (s in names(shares)) {
      expected <- expected + expected_unattributed(p[[s]], shares[[s]])
    }

    rest <- p$unattributed - expected
    shares[new_source] <- rest / (p[[new_source]] + rest)
  }
  shares
}
```

## Завдання 2. Оцінка A/B тесту частоти імейлів

**Рекомендація:** надсилати імейли вдвічі частіше лише новим користувачам; старим лишити частоту як є; тест для нових продовжити, щоб перевірити ефект на виручку.

**Відповіді на додаткові питання:**
1. **Чи достатньо даних:** для старих — так; для виручки нових — ні: тест упевнено помічає зміну балу нових від ~9%.
2. **Чи можна було закрити тест раніше:** ні — на 08.08, 15.08, 22.08 і 25.08 результат не перетинав меж, після яких зупинка коректна.
3. **Чи варто застосувати CUPED:** так, для старих — точність зросла приблизно втричі, і CUPED прибрав хибний плюс виручки (+6,9% без нього, −7,1% з ним), що виникав через нерівність груп ще до тесту. Для нових неможливий: у них нема даних до тесту.
4. **Які дані допомогли б оцінити тест швидше:** події самих імейлів — відправки, відкриття, кліки, відписки.

### Результат
Зміна в групі b (імейли вдвічі частіше) порівняно з a, %, у дужках — 95% діапазон. Користувачі зі згодою на імейли.

| | Виручка | Частка платників | Активні дні | Прочитані епізоди | Бал |
|---|---|---|---|---|---|
| **Нові**, перші 7 днів | +6,0 (−3,2; +16,5) | +2,5 (−4,1; +9,4) | **+6,5 (+5,7; +7,2)** | **+6,2 (+4,4; +8,1)** | +5,5 (−0,3; +11,9) |
| **Старі**, 01–25.08 | **−7,1 (−12,1; −1,9)** | +1,0 (−1,5; +3,4) | **−3,3 (−6,1; −0,4)** | **−12,3 (−15,9; −8,7)** | **−4,3 (−7,4; −1,2)** |
| **Разом** | | | | | +0,6 (−2,6; +4,1) |

- Жирне — діапазон не зачіпає 0, ефект надійний.
- Нові: активність зросла надійно; бал +5,5% (p = 0,06) — на межі доведеного; виручка — не доведено. Рекомендація для нових спирається на активність.
- Старі: падають виручка, активні дні й читання; найсильніше — на iOS (бал −8,2%).
- «Разом» близько нуля, бо плюс нових і мінус старих гасять одне одного.

### Як влаштований тест

| | Старі | Нові |
|---|---|---|
| Реєстрація | до 01.08.2022 | 01.08–19.08.2022 |
| Поділ a / b | 70 / 30 | 50 / 50 |
| Частіші імейли в b | з 01.08 | з дня реєстрації |
| Зі згодою на імейли, a / b | 47 469 / 20 345 | 34 273 / 34 237 |
| Період оцінки | 01.08–25.08, база 18.07–31.07 | 7 днів від реєстрації |

- Поділ на групи коректний: частки відповідають очікуваним, групи однакові за країною, ОС і згодою.
- Імейли отримують лише ті, хто дав згоду (`is_validated` = TRUE, 35%). Решта — контроль: у них ефекту бути не може, і його нема (бал нових −0,2%, старих +0,2%, обидва діапазони містять 0).
- Нові, зареєстровані 20–24.08, не входять в оцінку: до кінця даних у них менше 7 днів.

### Особливості даних і як їх оброблено
- **14.08 і 15.08 — нуль оплат** при звичайних візитах і читанні: схоже на втрату даних; ці дні виключено з виручки в обох групах.
- **Старі групи b активніші ще до тесту** (липень: виручка +23%, візити +4%) — і серед тих, хто імейлів не отримує. Тобто це нерівність складу, а не ефект імейлів; для старих порівнюється зміна відносно бази 18–31.07 (CUPED).
- **10% платників дають 51% виручки:** виручку вище 99,9-го перцентиля рахуємо на рівні порогу (нові — 360, 59 людей, −1,4% виручки; старі — 1 060, 67 людей, −1,1%).
- **Нові пробули в тесті від 1 до 25 днів:** усіх нових порівнюємо за однакові 7 днів від реєстрації.
- **`country_code` і `default_os` зв'язані:** країна 1 — лише android, 3 — лише desktop; розрізів 4, а не 9.

### Метод
- **Метрики на користувача:** виручка, частка платників, активні дні (дні з візитом), прочитані епізоди.
- **Бал** = 0,5 × зміна виручки + 0,2 × зміна частки платників + 0,3 × зміна активних днів; ваги задані до розрахунку.
- **Ефект** = (середнє b − середнє a) / середнє a. Старі — з CUPED: від метрики в тесті віднімається частина, передбачувана тією ж метрикою в базі.
- **Діапазони** — бутстреп по користувачах, 10 000 повторів.
- **Правило рекомендації, записане до розрахунку:** бал надійно > 0 і активні дні не впали → частіші імейли; активні дні надійно впали → не надсилати частіше цій групі; ефекти нових і старих протилежні → окремі рекомендації.
- Критерії, метрики й правило рішення записані й закомічені до розрахунку: [протокол](hypotheses/t2-ab-test.md).

*⚠ Даних про самі імейли (відправки, відкриття, відписки) нема: ризик втоми від розсилки видно лише через активність. Тест тривав 25 днів; частина негативу старих може бути реакцією на різку зміну частоти.*

### Код
Метрики на користувача — SQL на DuckDB прямо по csv (`task2/sql/02_user_metrics.sql`, фрагмент):

```sql
sum(t.amount) filter (where t.date between w.test_start and w.test_end
                        and t.date not in (date '2022-08-14', date '2022-08-15')) as revenue,
sum(t.amount) filter (where t.date between w.base_start and w.base_end)         as revenue_base
```

CUPED у розрахунку ефекту (`task2/ab_test.ipynb`, фрагмент):

```python
# прибираємо різницю між групами, яка була ще до тесту
x = df[m + "_base"].to_numpy(float)
x_all, y_all = wmean(x, weights), wmean(y, weights)
# theta: на скільки більше в тесті, якщо в базі на 1 більше (коваріація / дисперсія)
theta = (wmean(x * y, weights) - x_all * y_all) / (wmean(x * x, weights) - x_all ** 2)
mean_a = mean_a - theta * (wmean(x[~in_b], w_a) - x_all)
mean_b = mean_b - theta * (wmean(x[in_b], w_b) - x_all)
```

Звірка SQL-таблиць із сирими даними — 12 перевірок, усі з нульовою різницею (`task2/sql/99_checks.sql`).
